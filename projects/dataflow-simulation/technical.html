Medallion layers

Layer 01 · Raw

operational_raw

Bootstrap-loaded once from the master CSVs, never modified.

Layer 02 · Operational

operational

Populated incrementally, one calendar month per pipeline batch.

Layer 03 · Silver

silver

Cleaned views: hashes PII (email → hashed_email), derives processing_time and delivery_time, flags orders with inconsistent inventory timestamps.

Layer 04 · Gold

gold (dbt)

Business marts and ML feature tables, materialized as indexed tables.

Gold marts and ML features

mart_sales_revenue

Order-item grain revenue with gross margin, discount %, and status buckets (realized, returned, cancelled, lost-to-stockout).

mart_logistics_sla

Package-level delivery mart with processing and delivery time in days and SLA breach flags (processing over 2 days, delivery over 5).

mart_user_funnel

Session-grain funnel from silver.events (home → department → product → cart → purchase) with bounce and cart-abandonment flags.

ml_customer_churn_*

Training and inference sets: RFM, delivery-experience, and web-behavior features with a 90-day time-boundary cutoff so training never leaks future data.

ml_session_conversion_*

Session-level training and inference features for predicting purchase conversion.

All Gold tables have unique indexes and are tested with dbt unique and not_null tests (models/schema.yml).

Machine learning pipelines

Two independent use cases

Same structure, two problems

data_loader→preprocessor→model_trainer→model_evaluator→batch_inference→inference_evaluator

Customer churn: XGBoost binary classifier; churn means no order in the 90 days before the current simulation date. Session conversion: binary classifier predicting whether a browsing session converts to a purchase.

Trainer

Model selection, not just fit()

  • Optuna tunes n_estimators, max_depth, learning_rate (5 trials, maximizing PR-AUC on a validation split).
  • Dynamic scale_pos_weight from the training split handles class imbalance.
  • Decision threshold maximizes macro F1 on validation.
  • Refit on the full training set; every run auto-versions its artifact (customer_churn_model_v{N}.joblib).
Champion / challenger

A quality gate on every run

A model becomes champion only if its macro F1 beats a trivial majority-class baseline and the current champion. Every run, champion or not, is recorded in the Supabase model_metrics table with metrics, best hyperparameters, and evaluation plots.

Event-driven retraining

Not a wall-clock schedule

BranchPythonOperator retrains only when the batch number is a multiple of 6, otherwise the DAG short-circuits to a no-op. Inference runs on every batch through separate DAGs.

Orchestration

Six Airflow DAGs coordinate the pipeline.

operational_incremental_loadingEvery 3 minLoads the next month into operational, tracks progress in pipeline_metadata, then triggers the Gold pipeline.
dbt_gold_pipelineTriggered by loaderdbt run + dbt test, syncs marts to Supabase, exports Parquet, fans out to all four ML DAGs with batch number and simulation month.
ml_churn_training_pipelineWith batch contextRetrains the churn model every 6 batches (branch), otherwise skips.
ml_churn_inference_pipelineWith batch contextBatch inference every batch, then evaluates against realized outcomes.
ml_session_conversion_training_pipelineWith batch contextSame retraining pattern for the conversion model.
ml_session_conversion_inference_pipelineWith batch contextRuns conversion inference every batch.

All DAGs report through shared success and failure callbacks.

Implementation notes

The redis and airflow-worker services exist in docker-compose but are disabled; the project runs on LocalExecutor, not a distributed executor. ML training uses the host Docker daemon (DooD), which is why the Airflow image installs the Docker CLI and mounts the Docker socket.
